# shapez.io DEMO + ALL SHAPE YOU NEED 求解器

两件事：

1. `demo/` —— 官方网页版 shapez.io DEMO 的离线镜像（本地可玩）
2. `solver/` —— **ALL SHAPE YOU NEED 求解器**：输入一个地图种子，输出整条战役需要的所有图形的一张图纸（建筑坐标 + 物料流 + 材料表），每台机器的产出都会被复算校验

> 依据是游戏设定：**您生产过的所有图形都会被用于解锁升级**。所以正确打法是一次把整条战役要的 shape 全造出来、不拆旧工厂——求解器就按这个前提排一张图。
>
> 两部分互不依赖：`demo/` 是原样镜像，求解器独立运行，存档通过网页上的文件上传读取，不需要和游戏同源。

## 运行环境

- **Bun ≥ 1.4.4** —— 唯一的运行时。`solver/` 的源码全部是 TypeScript（唯一例外是 vendor 进来的 `lz_factory.js`），`tsconfig.json` 开 `strict` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`；Bun 直接执行源码，**没有构建步骤、没有打包器**。
- **布线器是 Rust/wasm**：`native/router` 编成已提交的 `solver/router.wasm`（改 Rust 后跑 `bun run build:router`）；CLI、测试与 `check:tunnels` 启动时同步加载，网页 worker 从 `/router.wasm` 异步加载。运行时仍然零 npm 依赖。
- `bun install` —— 只装一个 devDependency `@types/bun`；**运行时零依赖**（只用 `node:` 内置模块和相对 import）。
- `bun check` —— 类型门禁（Bun 自带的 TypeScript 检查器；不装 `typescript` 包）。
- `bun run test` —— 回归测试，182 项检查；`bun run test:quick` 只跑单元部分，147 项；`bun run verify` = `bun check` + 完整测试。

| 文件 | 作用 |
| --- | --- |
| `solver/cli.ts` | 命令行入口（`bun run cli`）；在 `solver/` 里也可以直接 `bun cli.ts` |
| `solver/server.ts` | 网页 UI + JSON API（`bun run serve`） |
| `solver/src/*.ts` | 求解器内核：形状代数、搜索、地图、布局、图纸 |
| `solver/src/lz_factory.js` | 上游 LZ-String 原样 vendor（唯一保留的 `.js`；`lz_factory.d.ts` 补类型） |
| `native/router/` | Rust 布线器；`bun run build:router` → `solver/router.wasm` |
| `solver/test/run-tests.ts` | 自定义回归测试（`bun run test`），`fuzz.ts` 是随机对拍 |
| `solver/web/app.ts` | 浏览器端 UI；请求 `/web/app.js` 时由 Bun 服务器现转译，不落盘 |

## 输入 seed，产出图纸

```bash
bun run cli all 47742             # → plan-47742.svg（DEMO 需求表 · 26 种）
bun run cli all 47742 --set=full  # 完整版需求表 · 34 种
bun run cli all 47742 --until=9   # 只画第 9 关时已解锁的产线
```

- 图纸 = 放置清单（tile 坐标）+ 物料流（哪台机器的哪个口接到哪个口、多少格）+ 材料表 + 一张按游戏内元素标注的 SVG（资源色矿脉、形状图标、中心）。
- `--until=N` 只画第 N 关时能建的工厂：求解器不会再用更晚解锁的机器（四向切割机、堆叠器、四色上色器等），需要更高关卡或本版本根本没有的机器会标「要 L10+」/「不可建」，而不是硬画出来。
- 种子决定矿脉分布：`S`/`W` 矿脉只在地图外围出现，扫描半径默认自动翻倍，直到需求表要的形状字母都能找到（`--radius=N` 可固定）。
- 网页版：`bun run serve`（默认 8099，`--port=N` 可改）→ 打开 <http://127.0.0.1:8099/>，在「地图种子」里填数字，点「生成全体图纸」。

## 2. 求解器核心（单图形）

```bash
# 命令行
bun run cli solve "RuCw--Cw:----Ru--"
bun run cli solve "CbCuCbCu:Sr------:--CrSrCr:CwCwCwCw" --json
bun run cli solve "Cu------" --level=demo:6      # 只用第 6 关时已解锁的建筑
bun run cli render "RuCw--Cw"
bun run cli levels --game
bun run cli check                                 # CLI 别名，等价于 bun run test

# 网页 UI + JSON API
bun run serve
# 打开 http://127.0.0.1:8099/
# GET /api/solve?shape=RuCw--Cw:----Ru--&buildings=cutter,stacker
```

单图形的「生产方案」除了 plan 步骤，还会列出**色料链**和**材料表**：
`p` 这种混合色不是 plan 步骤，但每个上色口都要一台混色器 + 两台基础色矿机；
`w` 要两级混色（先 r+g 再 +b）。材料表按 `expandPlanTree` 展开后的机器数计，
和图纸的 BOM 完全一致（共享子方案会按消费者复制）。

### shape code 语义（与游戏 1.5.7 完全一致）

- 象限顺序 `q0=右上, q1=右下, q2=左下, q3=左上`；每层 8 个字符 = 4 × (形状, 颜色)
- 形状 `C` 圆 / `R` 方 / `S` 星 / `W` 风车；颜色 `r g b y p c w u`，`--` 表示空位
- 例：`RuCw--Cw:----Ru--` = 底层 q0 方(无色)、q1 圆(白)、q3 圆(白)，上层 q2 方(无色)

### 建筑语义（照抄官方实现）

- **堆叠器**：按各象限「上层最低层 − 下层最高层」求最小间隙 `g`，把上层放到层偏移 `max(1 - g, 0)`（`g` 已经 ≥1 时不动）；合并后超过 4 层会被截断
- **切割机**：产出 `{2,3}` 和 `{0,1}` 两半；切完为空的层会被压缩掉（层号前移）
- **四向切割机**：一次产出 4 个单象限
- **旋转器**：CW / CCW / 180°
- **上色器**：整块染一色；**四色上色器**：按象限分别上色（空的象限传 null 保留原色）
- **混色器**：两个颜色入口，输出按游戏规则按位或（r+g=黄、r+b=紫、g+b=青，再 +b=白）

### 算法

按建筑数成本的递归分解（每个候选都用真实堆叠模拟校验，最后再整体复算一遍；成本只是搜索标量，不是优解判据——优解定义见 `docs/adr/0001-optimal-plan-pareto.md`）：

1. **base**：未上色的整块形状（采矿机）
2. **atom**：单层形状按象限拆块 → 各块切割/上色 → 堆叠（含"整层上色 vs 逐块上色"取优）
3. **整体上色 / 四色上色**：先去色求几何，再加一步染色
4. **旋转**：注意方向要取反——要造 `rot(shape, dir)`，最后一步是 `opposite(dir)`
5. **前缀堆叠**：`B = 前 k 层`，`T = 其余层`，且 `stack(B,T) === target`
6. **脚手架 + 切割**：目标只占半个形状时，先在会被切掉的那半边加一列"脚手架"把层高撑开，堆完再切掉（Level 20 的悬浮方块技巧）
7. **象限窗口拆分**：下层保留"某象限子集"的前 k 层，其余给上层；k=0 时就是同层合并（Level 20/26 的关键手法）
8. **兜底**：全组合拆分（受预算限制）

失败会缓存（被环检测影响的不缓存）；预算默认 30k 个状态，`--budget=N` 可调。超预算但已找到方案时会标注「可能次优」。注意：`aborted` 只是预算标记，不构成优解判据；优解见 ADR-0001。

- 图纸端口表：逐项对照官方 `ItemEjector/ItemAcceptor` 的 slot 位置（四色上色器的颜色入口在底部）
- 多出口槽位：`cutHalf` side 1、`cutQuad` q1/q3 的连线从正确出口出发
- 9 个 DEMO 关卡目标：按各关解锁的建筑求解，全部通过

## 3. 读地图 → 出图纸

```bash
# 读存档：savegame-*.bin 原始内容（或直接给种子）
bun run cli map --save=savegame.bin --radius=2
bun run cli map --seed=47742 --radius=3

# 一次解出「所有需要的图形」，所有工厂共用一张地图和同一个中心
bun run cli all 47742 --out=plan-all.svg
```

- **存档解码**：`"\x01" + LZ-String-base64( "crc32-…" + JSON )`，JSON 里是游戏自己的 key/value 内联格式；`solver/src/savegame.ts` 解出 `dump.map.seed` 和中心位置。
- **地图重建**：`solver/src/map.ts` 是 `map_chunk.js` 的逐行移植（ALEA RNG、`${chunkX}|${chunkY}|${seed}`、预置的 Cu/Ru/红/绿/星矿脉、圆的叠加算法）。实测与游戏画面完全对齐（Cu 在左下、Ru 在右上、红在右下、绿在左上）。
- **图纸**：`solver/src/layout.ts`（瓦片世界：几何、端口、路由、地图状态）+ `solver/src/placement.ts`（落位与布线）+ `solver/src/schematic.ts`（出图）
  - 每个采矿机自动落到最近的对应矿脉上（给出坐标和距离）
  - 加工建筑按依赖深度排布，避开采矿脉，给出每个建筑的 tile 坐标
  - 加工建筑的朝向在 4 个 90° 方向里选：先试游戏默认朝向，摆不下、或它的输入 / 通往中心的带布不通就换一个方向；端口和端口外的引带格跟着一起转（`portCells(..., rot)`）
  - 连接按游戏真实的输入/输出口位置计算（切割机 2×1、堆叠器 2×1、上色器 2×1、四色上色器 4×1、混色器 2×1、旋转器/采矿机 1×1）
  - 颜色供应：基础色由矿脉上的采矿机给出，混合色由混色器链给出（p=r+b、y=r+g、c=g+b、w=先 r+g 再 +b），每条都接到上色器的颜色入口
  - 输出 SVG 只用游戏地图视图自己的画法：矿脉用主题资源色 + 游戏形状图标；建筑是 `getSilhouetteColor` 的**整块剪影**（采矿机紫、切割机绿、旋转器青、堆叠器黄绿、上色器棕、混色器卡其、垃圾桶红），有 3×3 挖空的零件（采矿机圆环、旋转器、垃圾桶 U 形）按 `getSpecialOverlayRenderMatrix` 画，不自造图标或文字贴图；中心是红色 4×4 + 「中心」；输入口画方口、颜色入口画同色圆点（输出口不另标，带子从端口走）；传送带按 router 的逐格路径画游戏地图的深灰带色（`chunkOverview.beltColor = #777`）；隧道按游戏地图视图的 sender 蓝 / receiver 绿 3×3 覆盖矩阵画，地下段不画带。1 tile = 22 px，容器内滚动查看
  - **逐格布线**：`routeBelt()` 在 tile 网格上按真实零件尺寸布线——机器本体、所有端口和端口外的引带格都是障碍；两条带交叉要隧道（L6 解锁，且必须垂直）。每个零件落地前先对它的每条输入（以及最终成品进中心的那条）做一次**试布**，布不通就换朝向 / 换位置，所以「画得出来」等于「照着铺得出来」。真布不通的连接**不画线**，只在两个端口上打红色 ✕ 并报「布线失败 N 条」——画一条假带会让人铺出一条没有出口的残带，机器第一件货就堵。隧道的搜索状态带 phase：sender/receiver 必须落在直行段上，跨度不超过一级隧道的 5 格（中间最多 4 格地下），跨度内不得有同向隧道口（会劫持/截断链接），隧道口占格、不再当地面带；`bun run check:tunnels` 会独立重算整张战役的这些约束
  - **产能账本**：`solver/src/rates.ts` 里是游戏自己的速率（`getProcessorBaseSpeed` = `beltSpeed 2` × 升级 × `buildingSpeeds`，矿机 0.4/s、切割 0.5/s、旋转 2/s、堆叠 0.25/s、上色 2/6/s、四色上色 1/s、混色 0.4/s、带 2/s；升级等级 1）。一座厂 = 一条链，最慢的机器决定产能，所以每张图都给出「多少/分 + 多久交完这条图形要求的数量」
  - **供给定容与运输缺口**：色料按实际需求定容（每个源 0.4/s；`y/p/c` 消耗两台，`w = mix(mix(r,g),b)` 把需求推到 `y` 和 `b`），并报出还需几台矿机/混色器、一个输出口挂多条带要几个分流节点、进带数超过中心 16 个入口格时要几个并带
  - **解锁门槛**：奖励是「通关后」才给的，所以平衡器 L4、隧道 L6、上色器 L7、混色器 L9 才能真正用（试玩版与完整版前 5 关一致）；试玩版没有堆叠器，需要它的图形标「不可建」。每个工段都标出「最早在第几关可建」，混合色会把混色器的 L9 算进去（例如青色 `ScScScSc` 是 L9，不是上色器的 L7）
  - **拓扑合法化**：游戏里一个输出口只能接一条带，所以 `expandPlanTree()` 会把被多个父节点复用的子方案按消费者各复制一份（零件免费）；同一输入的多个切割步骤是同一台切割机的不同出口槽（四向切割机一次弹出 4 个象限、切割机两半各一个槽），`fuseCuts()` 把它们合成一台、按槽接线，只复制同槽的消费者。色料分两种：同一工厂里同色的 2 个以上色口共享一条网（L20 分流器解锁后）——每口仍一条链（0.4/s），链锚在组内第一台的基底矿机、在矿脉侧用合流器并成一条 trunk（每 5 口一条，受 2/s 限制），进块后用分流器按端口朝向逐个分流；单口的组、以及 L20 之前，全部退回每口一链。结果是整张图 **0 个多带出口**；中心有 16 个入口格，工厂数超过时才需要并带（L4 后可用平衡器）
  - **废料必须排掉**：切割机有 2 个（四向 4 个）出口，没接的那个会积压并让机器停转，所以每个没被方案用到的出口都配一个垃圾桶（1×1、四面可收、和切割机一起在 L1 解锁）；喂中心也可以，但中心只有 16 个入口格，优先用垃圾桶

## 零件清单：游戏里 28 种，我们建模哪些

`ref/buildings/*.js` 是游戏的全部零件。做一张纯物料图纸只需要其中一部分，剩下的是**刻意不做**的 —— 这张表就是那条界线，不要再靠猜。

| 游戏零件 | 尺寸 | 我们 | 说明 |
|---|---|---|---|
| miner 采矿机 | 1×1 | ✅ `base` | 只落在真实矿脉格上；单块矿脉的矿机数上限按「每台要一个独立出口」算 |
| belt 传送带 | 1×1 | ✅ 逐格布线 | 走 `routeBelt()` 的最短路；交叉处用隧道（L6+），无解只在两端端口打红 ✕，不画假带 |
| balancer 平衡器（本体） | 2×1 | ❌ 只报缺口 | 2 进 2 出；L4 解锁（`reward_balancer`）；只在并带/分流缺口里计数 |
| balancer·merger / merger-inverse | 1×1 | ✅ `merger` | 2 进 1 出（建模一个镜像方向 + 四向旋转）；需 `reward_merger` = 完整版 L10，试玩版没有这个奖励；共享色料网的并带树用它 |
| balancer·splitter / splitter-inverse | 1×1 | ✅ `splitter` | 1 进 2 出（同上）；需 `reward_splitter` = 完整版 L20；共享色料网的块内分流用它，未解锁时退回每口一链 |
| underground_belt 隧道 | 跨 5 / 9 | ✅ 一级（跨 5） | 一级 L6 解锁（`reward_tunnel`）；路线按 sender/receiver 直行、跨度 ≤ 5、同向口不劫持来搜索，二级（跨 9）不建模 |
| cutter 切割机 | 2×1 | ✅ `cutHalf` | 2 个出口用 1 个，另 1 个接垃圾桶 |
| cutterQuad 四向切割机 | 4×1 | ✅ `cutQuad` | 4 个出口用 1 个，另 3 个接垃圾桶 |

### 一次解出「所有需要的图形」（`all`）

游戏里写着：**“您生产过的所有图形都会被用于解锁升级”** —— 所以正确打法是别拆旧工厂，一次把整条战役要的 shape 都造出来。`all` 就是干这个的，输入只有地图种子：

```bash
bun run cli all 47742                    # → plan-47742.svg（DEMO 26 种）
bun run cli all 47742 --set=full         # 完整版 34 种
bun run cli all 47742 --out=base.svg     # 指定图纸路径
bun run cli all --save=savegame.bin      # 用存档里的真实种子和中心
bun run cli all --code=CuCuCuCu,RuCw--Cw:----Ru-- --seed=47742
```

- **需求表**（`solver/src/needs.ts`）＝ DEMO/正式版关卡目标 + 4 条升级线（传送带 / 采矿机 / 加工建筑 / 上色）每一档要的 shape，去重后一次解完：试玩版 26 种，正式版 34 种。
- **矿脉**（`solver/src/map.ts`）：地图按种子重建。风车（`W`）/星星（`S`）矿脉只在地图外围生成，`scanForTypes` 从半径 8（正式版 10）开始翻倍，直到需求表用到的形状字母都出现（上限 32），并报出实际半径；固定 `--radius=N` 时缺的字母会被明确警告。
- **排布**（`solver/src/campaign.ts`）：所有工厂排在同一张地图上、共用同一个中心。每个工厂的窗口先锚定到它自己矿脉的质心（`placement.ts` `factoryAnchor`），再在附近找一块不压矿脉、不压已有建筑的空地——所以矿脉到工厂的带子是最短的一段；采矿机落在块附近最近且还空着的矿脉格（同一矿脉可以插多台），工厂的产出各自一条腿回中心（入口挤时按 2/s 上限合流）。加工建筑按依赖深度排布，多工厂之间不会重叠；每个建筑的端口格会被预留，后来排的工厂不会把建筑盖在接口上。色料链按工厂内同色口共享一条网来建（L20 分流器解锁后），工厂之间不共用（F30/F39）。整张图的 `World`、建图后的跨厂修补与带格/色源账目都留在这个 module 里：`planCampaign` 交出的 `sheet` 就是图纸与报表本身（F52）。
- **输出**：每种 shape 的建筑数 / 传送带格数（不含隧道与平衡器）/ 需求来源，加总材料表与颜色来源，以及一张合并图纸：每个工厂框的左上角画该工厂的目标 shape 图标（游戏内形状渲染），不写自造的编号或 shape 代码；中心画成游戏里的红色 4×4 建筑 + `中心` 标签。
- 不给 `--out`（且不是 `--json`）时默认写 `plan-<seed>.svg`。

网页版：<http://127.0.0.1:8099/>（`bun run serve`，默认 8099，和 `demo/` 完全独立；Bun 服务器把 `/web/app.js` 的请求转译成 `solver/web/app.ts`，所以没有构建步骤）。界面分两个视图：

- **SHAPE 配方图**：输入 shape code → 生成工序依赖图，按依赖波次从左到右排成一行（不折行，横向拖动/缩放），箭头指向下游；混色器与色料矿机也画在同一张图里，最终产物沿末段连线送进图最右的 `中心 HUB`。跨波次的依赖（跳过一列以上）从图底部的独立通道绕行，不会压在中间卡片下面。「一张卡 = 一台机器」，卡片主体是该建筑的官方贴图（`solver/web/assets/buildings/`，裁自 demo 图集 atlas0_hq），所有贴图按同一个像素比例绘制，所以占地 1×1 的采矿机明显小于 4×1 的四向切割机、4×4 的中心更大；产物不画在卡上，而是跟着连线走——连线中点的图形就是这条线上的产物，颜色链的线用颜色描边、中点是一个色点——输入只由入边表达。同一台切割机的多个出口**共用一张卡**（卡上标 `2 个出口`），分叉发生在卡后：每个出口各引一条线，所以一台机器永远只有一条入线；波次按**机器**算——整台机器等它最早被需要的那个消费者——cost 与材料表按一台算。堆叠器的入边在目标侧标 `下层` / `上层`；色料卡片标注它的输出颜色与服务的上色口（如 `v16 端口2`），一台四色上色器的两个同色端口就是两条链，卡片编号不同。
- **ALL SHAPE YOU NEED 图纸**：填地图种子 → 点「生成全体图纸」；图纸支持滚轮缩放、拖动平移、双击复位，图例钉在左上角。「读取存档（可选）」用文件上传拿真实的中心位置：支持 Electron 版的 `savegame-*.bin`，或浏览器 IndexedDB `app_storage/files` 里的原始内容（DevTools → Application → IndexedDB 复制出来存成文件即可）。不传存档就按种子画。

### 局限

- **不是所有 shape 都能造**。例如 `Cu------:--Cu----:----Cu--`（每层只占一个象限、彼此完全不重叠）：堆叠器要靠"两个形状在同一象限重叠"才能把上层撑开一层，这种目标在游戏里也造不出来。求解器会明确报告找不到方案（同时说明可能只是预算不足）。
- 只保证「建筑序列能产出该 shape」；朝向在上表的 4 个 90° 方向里挑能布线的一个，吞吐量按游戏额定速率估算。
- 复杂目标可能吃满预算返回次优解（UI 和 JSON 都会标注 `aborted`）；`aborted` 只是预算标记，不是优解判据。
- **优解定义**：交付效率（送入中心/秒）与占用格的帕累托前沿；交付上限 = 中心 16 个入口 × 2/s = 32/s；设施免费、地图无限、带速固定无衰减、带满即流式无延迟。当前求解器只按建筑数找一个方案，不计算前沿（`docs/adr/0001-optimal-plan-pareto.md`）。
- 图纸保证建筑坐标、朝向、接口和逐格传送带路径：`routeBelt()` 按真实零件尺寸布线，交叉处放**隧道**（L6+，垂直跨越；sender/receiver 直行、跨度 ≤ 5 格、同向口不重叠），布不通的连接只在两端端口打**红色 ✕** 并报「布线失败 N 条」，不会假装接通，也不会画出会堵机器的残带。原版没有蓝图字符串可以导入，铺带仍要照着图自己点。
- 极密集的色料链和中心入口仍可能把个别端口堵死；这类连接会如实报告并标红 ✕，需要手动挪一下布局。实测 seed 47742：试玩版需求表 48 条连接全部布通；完整版需求表也是 **0 条失败**——隧道允许从建筑下方穿过（F44），加上建图后的 campaign 级 rip-up 重放（F45）之后。没有这两步时完整版分别有 33 条和 8 条失败。

### 关于那篇 arXiv 论文

`arXiv:2611.17309v1`《Classical Energies Learn to Reason 1,000x Faster than Looped Models》讲的是用能量模型（energy descent）解 Sudoku/Maze 这类**判定型谜题**。本项目的任务是**构造性综合**：要在 shapez 的建筑语义下找一条可执行、可逐步验证的生产链，而不是给一个解打分/去噪。因此没有采用学习式求解器；不过它提到的「能量/约束即模型」在更模糊的变体（比如带吞吐/布局约束的优化）里可能有借鉴价值。
