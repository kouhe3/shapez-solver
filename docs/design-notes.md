## 对求解器的含义

1. **主目标是时间，不是建筑数**：交付时间 = 需求量 / 产线额定速度；图纸与 BOM 是为这个时间服务的。
2. **不过河拆桥**：旧的形状产线可以继续为升级供货，所以战役图共用一张地图和一个中心，不默认拆旧厂。
3. **平衡器前后拓扑不同**：L4 之前不能分叉/汇合，扇出只能复制源或多拉几条带；L4 之后才能分叉，而中心始终只有 12 个入口面。
4. **核心入口有限，但多喂不阻塞**：超产直接送中心没有副作用，所以不需要精确配平——这是求解器不做产线平衡的依据。
5. **矿脉是有损的**：采矿机必须留出口，矿脉边缘的格子会浪费；`scanMap`/`scanForTypes` 只按可达矿脉估算，不把矿脉形状当精确资源。
6. **工程效率是下一层**：当前 `rates.ts` 只给额定速度（传送带 2/s、采矿机 0.4/s、色料源 0.4/s，升级 1），不建模带速升级、机器节拍、堆叠与拥堵。

## 已知缺口与回流条件

| 缺口 | 现状 | 回流条件 |
|---|---|---|
| 隧道跨度合法性 | `routeBelt` 只检查交叉格两条带垂直；sender/receiver 可以落在拐角，或两条隧道只隔 1 格地表（游戏建不出来）。实测 full 集 1907 crossings：senderTurn=182、receiverTurn=135 | 把「sender/receiver 前后各一步同向」与「同一隧道的地表间隔 ≥2 格」做成 `routeBelt` 的搜索约束，重跑全量回归 |
| items/s 与带速 | ETA 用额定速度，不建模带等级、堆叠、拥堵 | 需要产线级仿真时 |
| 平衡器/隧道不计入 BOM | `BUILDING_INFO` 只覆盖机器和垃圾桶 | 要把运输件纳入材料清单时 |
| 矿脉形状 | 只按 chunk/半径扫描矿脉，不逐格计算可采矿格 | 需要精确矿脉损耗时 |
**勘误（2026-11-15，隧道跨度合法性已修）**：第一条缺口已关闭。`routeBelt` 现在把隧道作为搜索状态（surface / underground 1..4 / receiver）处理：sender、receiver 前后各一步必须与隧道同向，sender→receiver 间距 ≤ 5 格（一级隧道，`undergroundBeltMaxTilesByTier[0]`），跨度内不得出现同向隧道口，隧道口占格且不再当地面带，路径不得自重叠。判据是独立校验器 `bun run check:tunnels`：seed 47742 的 demo 集 46/48、full 集 396/809 可布线，全部隧道违规计数为 0；旧图里的 452 条 link 中混有大量非法隧道，396 是合法规则下的可布线上限。详细事实见 `docs/facts.md` F16。


## 这是 NP 问题吗

不是严格意义上的「NP 完全」——仓库里没有归约证明，也不该凭感觉下这个结论。可以拆成两层看：

- **单图形状分解**（当前求解器真正解的部分）：层数 ≤4、象限 4 个，状态空间有限；`planShape` 是带预算的深度优先搜索，每个候选都用真实的 `S.stack`/`S.cut`/`S.paint` 重放，`verifyPlan` 再复算一遍。这是**有界组合搜索**，可判定、可验证，规模靠 `maxAttempts`/`splitCap` 控制。
- **整条战役的时间最优**（含产线复用、核心入口、平衡器/隧道拓扑）：这是**调度/资源分配**问题（连续时间、资源近似无限、入口有限），比单形状分解大一层。当前求解器没有解这一层，只给出每种形状的独立产线 + 额定速度 ETA。

所以：**现在是「已验证的单形状组合搜索 + 未建模的战役调度」**，不是「已经证明的 NP 问题」。
